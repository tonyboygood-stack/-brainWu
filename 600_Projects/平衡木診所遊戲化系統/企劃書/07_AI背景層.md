# 07 AI 背景層

> 2026-09-07 老吳提出：「我希望整個系統背後還是有 AI 的智慧幫忙，不用是即時性的，而是在背景有觸發點的完成一些任務，例如耗材統計、科學中藥消耗統計、收支統計等，然後每天經由統整給出完整的建議指示，例如叫多少藥等等。」

**這是原本五層模型（地圖／角色／任務／記錄／成長）之外的第六層。**

---

## 一、AI 做四種工作，難度與期別完全不同

| 類型 | 例子 | 需要的資料 | **系統現在有嗎** | 期別 |
|---|---|---|---|---|
| **敘事** | 每日診所日誌、里程碑小故事 | 任務紀錄、班表、備註、感謝卡 | ✅ **都有** | 第 2 期 |
| **統計** | 耗材用量、任務耗時趨勢 | 盤點數字、時間戳 | ⚠️ **要補欄位** | 第 1 期收集 |
| **預測建議** | 叫多少藥、何時該補貨 | 3–6 個月歷史 | ❌ **開幕時沒有** | 第 2 期以後 |
| **草擬** | 負評轉提案的措辭、公告草稿 | 老吳的收件匣 | ✅ 有 | 第 2 期 |

---

## 二、⚠️ 一個必須先講清楚的事實：資料還不存在

### 「叫多少藥」在開幕第一天做不到

不是技術問題，是**沒有歷史資料**。任何用量預測都需要至少 3–6 個月的實際消耗紀錄才會準。開幕第一個月的 AI 建議只會是瞎猜，而且瞎猜的叫貨建議會直接變成錢的損失。

> 這正好呼應 `index.md` 已經定的第 0 期哲學——「不能跳過去直接開發，會做出一套你想像中的診所」。
> **資料也一樣要先養。第 1 期的工作不是做預測，是開始收集。**

### 三類資料，來源與難度差很多

| 要統計的東西 | 資料在哪 | 難度 |
|---|---|---|
| **耗材消耗**（棉球、酒精、針具、床紙） | 01 已有「耗材盤點」「庫存盤點」任務——**但目前只記錄「有沒有做」，沒記錄「數字」** | 🟢 **簡單**：把盤點任務加上數字欄位即可 |
| **科學中藥消耗** | 在百會電腦的處方紀錄裡，本系統沒有 | 🟡 中：需匯出或人工月結登錄 |
| **收支統計** | 百會電腦 ＋ 會計師 | 🔴 難：牽涉帳務系統，且與本系統邊界衝突 |

### 建議的優先順序

1. **第 1 期就做**：耗材盤點任務加數字欄位 → **開始累積**
2. **第 1 期末**：科中消耗改成「每月人工登錄一次總量」——不接系統，用手輸入，一個月一次負擔極小
3. **第 2 期再說**：收支統計。它跟會計師的帳務系統重疊，而且屬於財務資料，建議**不要進這套系統**，留在你既有的 `600_Projects/東湖診所開業計畫/財務/`

> **收支不進系統，是我建議守住的另一條邊界。** 這套系統的角色是「員工 × 任務 × 時間」，一旦裝進收支，它就變成一個沒人維護得動的營運系統，而且員工端的裝置會碰到財務資料。

## 三、⭐ 耗材消耗率學習：AI 最實用的一條，而且會形成閉環

這是我認為第 2 期最有價值的功能，因為它**不只產出報告，還會產出任務**。

### 運作方式

```
盤點任務（填數字）
      ↓
系統比對上次盤點 → 算出「這段期間消耗了 X」
      ↓
累積 3–4 次後 → 得出「棉球平均每週消耗 Y」
      ↓
剩餘量低於安全水位時
      ↓
🔔 自動產生一個任務：「該叫棉球了（建議數量：Z）」
      ↓
助理看到任務 → 通知老吳 or 由「藥務聯繫」技能加給者直接處理
```

**這條的價值：**

- 把 AI 的洞察**變回任務**，回到員工看得到的地方，而不是躺在老吳的報告裡
- 直接餵養「技能晉升加給－藥務聯繫（+1,000/月）」這個既有職務——**她有工具可以把這件事做好**
- 缺貨是小診所最常見的營運失誤，而且完全可以預防

> 科學中藥的用量預測同理，只是資料來源是每月人工登錄的總量，精度較粗但足夠用。

### ⭐ 叫貨建議要整合藥廠資訊（2026-09-08 老吳補充）

老吳的思路：統計表單 ＋ 每日消耗 → 用藥趨勢 → **再整合不同家藥廠資訊** → 給出建議。

**好消息：供應商資料已經是結構化的了。** [[600_Projects/東湖診所開業計畫/耗材供應商|耗材供應商]] 已經有「品項／規格／批發價／售價」的表格，[[600_Projects/東湖診所開業計畫/藥材供應商|藥材供應商]] 有評估維度。這些可以直接匯入成 `suppliers` 與 `products` 兩張表。

**而且我在耗材供應商那份資料裡看到一個關鍵欄位：「滿 2000 免運」。**

這代表叫貨建議不能只算「什麼快用完了」，還要算**怎麼叫最划算**：

| 建議要考慮 | 例子 |
|---|---|
| 消耗率與剩餘天數 | 「棉球約剩 12 天」 |
| **免運門檻** | 「目前湊到 1,700，再 300 元免運——建議順便補 2 吋針一盒」 |
| **最小訂購量／包裝規格** | 針灸針是 100 支／盒，不能拆 |
| **跨供應商比價** | 同品項哪家便宜（漢柏 vs 其他） |
| 交期 | 提前幾天下單才不會斷貨 |

> **「湊免運」這件事看起來很小，但它是真金白銀，而且是人最容易算漏的。** 這正是 AI 該做的工作——不是聰明的判斷，是不會忘記的計算。
> 這也讓「技能晉升加給－藥務聯繫（+1,000/月）」那個職務變得具體：她有一份算好的清單可以執行，而不是憑印象叫貨。

## 三之二、⭐ 耗材盤點怎麼輸入才不折磨人（老吳 2026-09-08 提問）

老吳提了兩個方案並問我的看法。**我的答案是：兩個都要，但主力是第三個。**

### 三種輸入方式的實測性判斷

| 方案 | 速度 | 準確度 | 適合什麼 |
|---|---|---|---|
| **① 快捷按鈕**（我補的） | ⚡ 最快 | ✅ 100% | **常規品項**——就那 20–30 樣，點 `+1` 比講話快 |
| **② 語音自由輸入**（老吳方案一） | 快 | ⚠️ 中 | **非常規、突發**——「青草膏耗掉一桶」 |
| **③ 手寫單拍照**（老吳方案二） | 慢 | ⚠️ 低 | **憑證備援**，不當主要輸入 |

### 建議的組合：**按鈕為主，語音為輔，拍照當憑證**

```
盤點任務打開
   ↓
【常用品項面板】棉球 −1 │ 床紙 −1 │ 1吋針 −1 │ 酒精 −1 …
   ↓  （點一點就完成八成）
【🎤 其他（語音）】「青草膏耗掉一桶、枕頭巾一包沒了」
   ↓
【📷 拍照】（選配，留紙本憑證）
   ↓
✅ 確認清單：棉球 ×1 · 床紙 ×1 · 青草膏 ×1桶 · 枕頭巾 ×1包 —— 對嗎？
   ↓
存入統計表
```

### 為什麼主力是按鈕不是語音

耗材品項是**固定且有限的**（就那 20–30 樣）。固定選項用點的一定比用講的快，而且不會辨識錯。語音的價值在於處理「你沒預先列進按鈕的那些」——這才是它真正省事的地方。

### ⚠️ 語音輸入要先建 Typeless 個人字典

「青草膏」「枕頭巾」「一吋針」「仙峰藥布」這些詞，通用語音辨識一定會錯。
**Typeless 有個人字典功能，而且診所是共用帳戶——字典只要建一次，兩台裝置都生效。** 這正好用上。

→ 開幕前把耗材品項與藥名批次加進 Typeless 字典，這是一次性的十分鐘工作。

### ⚠️ 拍照 OCR 不要當主要輸入

手寫中文的 OCR 準確率遠低於印刷體，尤其藥名與數字混寫。**但拍照功能還是要做**——它的價值是**留下憑證**：日後帳目對不上時，有一張紙本照片可以回溯查證。

> 定位：拍照是**存檔**，不是**輸入**。

### ⭐ 最重要的一步：AI 解析後必須回顯「確認清單」

不管哪種輸入，AI 解析完都要跳出一張清單讓人核對後才存檔。

**這一步絕對不能省。** 因為這是庫存數字，錯了就叫錯貨、就是錢。而且確認只要兩秒——點一下「對」。

> 這也呼應第六節的鐵則：**AI 產出一律是草稿，人按確認。**

---

## 四、⚠️ 任務耗時分析：一條很容易滑向監控的線

系統會自然擁有每個任務「從開始到完成」的時間戳。這個資料很有價值，但**用錯方向就是監控**。

| ✅ 可以做 | ❌ 絕對不做 |
|---|---|
| 看**任務**的趨勢：「開診準備最近平均多花 8 分鐘」→ 流程哪裡卡住了 | 看**人**的比較：「A 比 B 快」 |
| 發現某任務長期超時 → 該拆解或簡化 | 把耗時做成個人考核指標 |
| 找出一天中最卡的時段 → 調整排班 | 提供任何「員工效率排名」的視圖 |

> **系統層面就不要做出「人的比較視圖」。** 不是靠自律不去看，是**根本不做那個畫面**。
> 一旦那個畫面存在，總有一天會在某個累的晚上被打開，然後這套系統的信任就沒了。
>
> 這也呼應 `index.md` 自己的警告：「遊戲化很容易變成監控。2 個人的診所，如果變成老闆在看你有沒有偷懶，會直接反效果。」

## 五、觸發時機（老吳要的「非即時、有觸發點」）

| 觸發 | AI 做什麼 | 給誰看 |
|---|---|---|
| **收診後**（最後一個收診任務完成） | 產出當日診所日誌 | 全員（公佈欄） |
| **每週日晚上** | 週報：任務完成率、備註摘要、待處理積壓、異常趨勢 | **僅老吳** |
| **每月最後一天** | 月結：耗材消耗、科中用量、建議叫貨清單、月度小結 | **僅老吳** |
| **盤點任務完成時** | 比對上次，更新消耗率模型 | 系統內部 |
| **庫存低於安全水位** | 自動產生「該叫貨了」任務 | 全員 |
| **里程碑觸發時** | 草擬小故事 | 老吳潤稿後上樹 |
| **收到負評時** | 草擬「轉提案」的中性措辭 | **僅老吳**，且必須他確認才送出 |
| **老吳手動** | 隨時問任何問題 | 老吳 |

## 六、一條鐵則：**AI 的產出一律是草稿，永遠不自動執行**

| 場景 | AI 給的 | 誰按下確認 |
|---|---|---|
| 叫貨建議 | 「建議叫棉球 20 盒」 | **老吳**（這是錢，而且缺藥會影響看診） |
| 負評轉提案 | 一段中性措辭草稿 | **老吳**（措辭一偏就變成指責，傷害收不回來） |
| 里程碑小故事 | 一段敘事草稿 | **老吳**（那是診所的歷史，該有人的溫度） |
| 每日診所日誌 | 完整一段 | 自動發布，但**老吳可事後補一句話或修改** |

> 唯一自動發布的是每日日誌，因為它只描述事實、不做判斷、不涉及錢。其餘都要人按確認。

## 七、每日日誌的三條寫作規則（重申，因為這是最關鍵的）

| 規則 | 為什麼 |
|---|---|
| **只寫事實，不評價人** | AI 一開始誇獎，誇獎就變廉價；一開始批評，這功能就死了 |
| **不寫沒做完的事** | 日誌是收尾，不是檢討。未完成屬於明天的待辦 |
| **不碰病人任何細節** | 只寫數字（今天 17 位），不寫個別病人的事 |

詳見 [[600_Projects/平衡木診所遊戲化系統/企劃書/06_診所公佈欄與每日日誌|06]] 第五節。

## 七之二、⭐ 「API 的 AI 會不會不懂我們的設計？」（2026-09-08 老吳提問）

> 老吳：「如果要額外再申請一個 API，它可能就不會知道我們的整個設計流程，以及背後一些診所、規劃相關的資訊。還是這其中有哪些我不太知道的技術上的部分？主要是很多環節，我希望也可以藉由像這樣跟你對話的方式，來修正跟完善。」

### 先澄清一個技術誤解

**API 呼叫的 Claude，和現在對話的 Claude，是同一個模型。差別不在能力，在「上下文」。**

我現在之所以知道診所的事，不是因為我「記得」——我沒有跨對話的記憶。是因為：

1. `CLAUDE.md` 被自動載入
2. 我用工具讀了 vault 裡的檔案（設計簡報、職缺說明書、供應商清單…）
3. 這次對話的歷史都在上下文裡

**API 呼叫可以做完全一樣的事：你餵什麼進去，它就知道什麼。**

### 所以解法是：**把企劃書本身當成 AI 的系統提示**

每日日誌的 API 呼叫實際上長這樣：

```
[系統提示]
  ← 00_總企劃.md 的摘要（診所背景、班表、人員、系統哲學）
  ← 06 的三條寫作規則、四種語氣、「一點期待一點畫面一點收尾一點溫度」
  ← 設計簡報的調性與禁忌
[今天的資料]
  ← SQL 查出來的當日任務、備註、班表、「今天值得記一筆」的投稿
[要求]
  ← 產出今天的日誌
```

> **這樣它知道的其實比一個新開的對話還多**——因為規則是被明確寫下來的，不是靠對話慢慢累積出來的。

### ⭐ Prompt 檔案化：讓「用對話修正」真的可行

建議在專案裡開一個資料夾：

```
600_Projects/平衡木診所遊戲化系統/prompts/
  ├─ 每日日誌.md
  ├─ 叫貨建議.md
  ├─ 台詞候選.md
  ├─ 里程碑小故事.md
  └─ 負評轉提案.md
```

**每個檔案就是那個功能的系統提示。系統呼叫 API 時讀這些檔案。**

好處：

| 好處 | 說明 |
|---|---|
| **你隨時可以自己改** | 就是一個 markdown 檔，不用碰程式 |
| **對話後我直接改檔案** | 「日誌太長了」→ 我改 `每日日誌.md` → 下次就短了 |
| **git 有版本記錄** | 改壞了可以回溯 |
| **效果不好就是改一個 md 檔的事** | 不是改程式、不是重新部署 |

> 這其實就是你已經在做的事的延伸——`CLAUDE.md`、`000_Agent/skills/` 都是同一個模式。**你已經很熟這套玩法了。**

### 完整的閉環（這就是你要的「用對話修正完善」）

```
   你跟我對話：「日誌寫得太文青了，實際一點」
            ↓
   我改 prompts/每日日誌.md
            ↓
   git commit → Obsidian Git 自動推送
            ↓
   當晚收診後，排程呼叫 API 讀到新規則
            ↓
   日誌變了
```

**你已經有全部的基礎設施**（vault ＋ git ＋ Obsidian Git 自動推送）。這個閉環不需要新東西。

### 兩種需求要分開，它們的解法不同

| | 需求 | 解法 |
|---|---|---|
| **A. 日常自動產出** | 每日日誌、叫貨建議、台詞候選 | 排程 ＋ API，無人值守 |
| **B. 設計的持續演化** | 「這個規則不對」「日誌太長」 | **就是現在這種對話** |

**B 是 A 的上游。** 你不需要在 A 裡面對話，你在 B 裡面對話，A 自動跟著變。

## 七之三、⭐ 但其實：第 1 期建議完全不做 API

上面講完之後，還有一個更重要的判斷——**大部分你想要的 AI 功能，根本不需要自動化。**

### 誠實地檢查：哪些真的需要「無人值守」？

| 功能 | 頻率 | 真的需要自動嗎 |
|---|---|---|
| **每日診所日誌** | 每天收診後 | ✅ **需要**——它要在收診那一刻出現在公佈欄，晚了就沒有儀式感 |
| 叫貨建議 | 一個月一次 | ❌ **不需要**——你自己開 Claude Code 說「幫我看這個月的庫存」就好 |
| 月結分析 | 一個月一次 | ❌ 不需要，同上 |
| 台詞候選 | 想到再說 | ❌ 不需要 |
| 里程碑小故事 | 幾個月一次 | ❌ 不需要 |
| 負評轉提案措辭 | 不定，且要你審 | ❌ 不需要 |

**只有「每日診所日誌」一項真的需要排程。其餘全部可以是「老吳打開對話問一句」。**

### 而且對話的效果更好

一個月一次的庫存分析，用對話做**比自動化做得更好**：

- 你可以追問（「為什麼建議叫這麼多？」）
- 可以當場改主意（「這家太貴，換一家看看」）
- 可以帶入系統不知道的資訊（「下個月我要休診一週」）
- 我可以直接讀 vault 裡的供應商檔案，不用先做資料匯入

> **自動化的價值在「頻繁 ＋ 規則明確 ＋ 不需要判斷」。**
> 叫貨建議三個條件都不符合——一個月一次不頻繁，而且需要判斷。**把它自動化是把一件本來做得很好的事做壞。**

### 建議的分期

| 期別 | 做法 |
|---|---|
| **第 1 期** | **完全不做 API。** 所有 AI 功能都用對話（Claude Code 讀 vault ＋ 讀資料庫）。**成本 NT$0**（用你既有的訂閱） |
| **第 2 期** | 只把「每日診所日誌」做成排程 API。這時候規則已經在第 1 期的對話中磨穩了，prompt 直接抄過去 |
| 之後 | 若真的有其他高頻需求再說 |

> **這個順序有個額外的好處：第 1 期用對話跑幾個月之後，你會很清楚知道日誌該長什麼樣。**
> 到時候寫進 `prompts/每日日誌.md` 的規則，是實際磨出來的，不是想像的。
>
> 這跟 index.md 的第 0 期哲學是同一件事——**先跑真的，再自動化。**

### 修正：AI 的年成本

既然第 1 期不做 API，[[600_Projects/平衡木診所遊戲化系統/企劃書/09_資料模型與技術規格|09]] 估的 AI API 年費 **第 1 期是 NT$0**。
第 2 期只跑每日日誌的話（每天一次、每次約 3K token），一年約 **NT$100–200**。

## 七之四、⭐⭐ 定案：做成 Skill ＋ Routine 排程（2026-09-08 老吳提案）

> 老吳：「每日診所日誌、叫貨單整理與建議、台詞候選，這些可以設計成一個 skill，經由 ROUTINE 排程每天定時（如下診）讀取當日後台收到的資訊、並跑一遍，並討論看看有哪些問題需要修正或更新。」

**這個方案比 API 路線好，而且好到可以把 API 那條路整個刪掉。**

### 為什麼比 API 好

| | API（Edge Function） | **Skill ＋ Routine** |
|---|---|---|
| 要不要寫程式 | 要（Edge Function、金鑰管理、部署） | ❌ **不用**，就是一個 markdown |
| 能不能用工具 | ❌ 只能收文字、回文字 | ✅ **可讀 vault、查資料庫、寫檔案、git commit** |
| 成本 | 額外 API 費用 | **用既有訂閱** |
| 修改規則 | 改 prompt 檔 ＋ 重新部署 | **直接改 skill 的 md** |
| 能不能「留問題給你討論」 | ❌ 單向 | ✅ **可以** ← 這是關鍵 |
| 老吳熟不熟 | 新東西 | ✅ **已經在用**（`good-morning`、`journal`、`handbook`） |

> 最後一條最重要。**這不是引進一個新技術，是把一個你每天在用的模式，多用一次。**

### Skill 設計草案：`clinic-daily`

**排程**：每天 23:00（見下方時間點的坑）

**流程**：

```
1. 讀取當日資料
     ├─ 資料庫（或第 0 期時直接讀 vault 的看板）
     └─ 當日任務、備註、班表、「今天值得記一筆」投稿、感謝卡、盤點數字

2. 【一定產出】每日診所日誌
     └─ 寫入公佈欄 ＋ 存進 vault

3. 【條件產出】庫存提醒
     └─ 只在「有品項低於安全水位」時才報，否則不出聲

4. 【條件產出】台詞候選
     └─ 只在「有新觸發狀態」時才產（接近升階／節氣／特殊天氣／剛收到感謝卡）

5. 【累積】待討論清單
     └─ 寫進一個檔案，隔天早上跟 good-morning 一起呈現
```

### ⚠️ 四個會出問題的地方

#### ① 「下診」的時間不固定，不能綁

| 班別 | 收診 |
|---|---|
| 週一、三、五 | 21:30 |
| 週二、四、六 | 17:30 |

而且會 delay。cron 是固定時間，綁不了「下診」這個事件。

**解法：固定每天 23:00 跑。** 兩種班別都保證已經收診，而且還在當天（不會跨過凌晨 4 點的營業日界線）。

> 若之後希望日誌「收診當下」就出現在公佈欄，那才需要事件觸發——但那是第 2 期的事，第 1 期 23:00 完全夠用。

#### ② 三件事的節奏不同，全部每天做會變噪音

| 項目 | 老吳的想法 | 我的建議 |
|---|---|---|
| 每日日誌 | 每天 | ✅ 每天 |
| **叫貨統計** | 「可能消耗很快，每日統計」 | ⚠️ **每天算，但只在低於水位時才提醒**——每天報一次完整庫存，看三天就會開始跳過 |
| **台詞候選** | 每天 | ⚠️ **改成條件觸發**——每天產 3–5 句，一個月就 150 句，你審不完。累積待審的東西會變成壓力 |

> **「每天跑」和「每天都要說話」是兩回事。** 一個好的 routine 大部分時候應該是安靜的——它只在有事的時候出聲。

#### ③ 排程要在哪裡跑

| | 需要電腦開著 | 能讀 vault |
|---|---|---|
| 本機排程 | ⚠️ **要**——但收診 21:30，你的電腦可能沒開 | ✅ 直接讀 |
| **雲端 routine** | ❌ 不用 | ✅ **因為你的 vault 就在 GitHub** |

**建議用雲端 routine**：clone vault → 讀資料 → 產出 → commit → push。你的 Obsidian Git 隔天會自動同步下來。

#### ④ Routine 不可以自己改東西

它可能會發現：「今天有 3 個任務從來沒人做過，是不是該停用？」

**那是觀察，不是授權。** 承前面的鐵則——**AI 產出一律是草稿，人按確認**。Routine 可以寫日誌、寫候選、寫觀察，**但不可以自己停用任務、改台詞、改設定、改門檻**。

### ⭐ 「討論看看有哪些問題需要修正」——這部分怎麼運作

這是老吳提案裡最有價值的一半，而且它有現成的出口：**接到 `good-morning`**。

```
   23:00  routine 跑完
            ↓
   把觀察寫進「待討論」清單
            ↓
   隔天早上你說「早安」
            ↓
   good-morning 一併呈現這些觀察
            ↓
   你想處理就跟我對話 → 我改 skill / 改企劃書 → commit
            ↓
   當晚的 routine 就用新規則
```

**這個閉環完全落在你既有的工作流裡，不需要任何新習慣。**

Routine 可能會提出的觀察類型：

| 類型 | 例子 |
|---|---|
| 任務健康度 | 「開診準備的『藥茶煎煮』連續兩週沒被勾選，是流程變了還是清單該改？」 |
| 內容疲乏 | 「這句台詞這個月出現 8 次，可能太頻繁」 |
| 資料異常 | 「棉球的消耗率跟上個月差 3 倍，可能盤點填錯」 |
| 積壓 | 「有 2 則紅色待處理備註超過 5 天沒人處理」 |
| 規則不合身 | 「診療區這個月的分母只有 4，50% 門檻可能太寬鬆」 |

> 最後一類特別有價值——**系統會自己回報「這個設計在現實中不合身」**，這正是第 0 期要養出來的東西。

### 結論：API 路線刪除

| 原方案 | 改為 |
|---|---|
| ~~Supabase Edge Function ＋ pg_cron ＋ Claude API~~ | **Skill ＋ 雲端 Routine** |
| ~~AI API 年費 NT$100–1,200~~ | **NT$0**（用既有訂閱） |
| ~~`prompts/` 資料夾~~ | 併入 skill 本身（skill 就是 prompt） |

## 八、技術路線

| 項目 | 建議 | 理由 |
|---|---|---|
| **執行方式** | **Skill ＋ 雲端 Routine，每天 23:00**（見七之四） | 不用寫程式、能用工具、能留問題給老吳討論 |
| 模型 | 敘事類用較強的模型；統計類用程式算，不用 AI | **統計不要交給 AI 算數字**，用 SQL 算，AI 只負責把結果寫成人話 |
| 成本 | **NT$0**，用既有訂閱 | |
| 失敗處理 | Routine 沒跑成功時公佈欄顯示「今天的日誌還在寫」，不影響任何核心功能 | AI 層必須是**可拆卸的**，壞了不能讓系統停擺 |

> **「統計不要交給 AI 算數字」這條很重要。** 消耗量、完成率、庫存這些要用 SQL 精確計算，AI 只負責把算好的結果寫成一段話。讓 AI 心算會出錯，而叫貨建議算錯就是真的錢。

## 九、第 1 期要先留好的東西（重點）

即使 AI 層是第 2 期，第 1 期**必須先把資料欄位留好**，否則第 2 期要回頭補半年的資料：

- [ ] 盤點類任務加 **數字欄位**（品項、數量、單位）
- [ ] 所有任務記錄 **開始時間戳 ＋ 完成時間戳**（不只完成時間）
- [ ] 心情留言板的資料結構（餵每日日誌）
- [ ] 每日班表、守備區、病人數的每日快照
- [ ] `daily_journals` 空表先建好
- [ ] 節氣靜態表先內建

> 這些欄位在第 1 期幾乎不花成本，但沒留的話，第 2 期的 AI 就沒有歷史可以學。
