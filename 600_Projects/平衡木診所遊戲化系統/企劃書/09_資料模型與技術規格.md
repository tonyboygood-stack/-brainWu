# 09 資料模型與技術規格

> 前八節的技術翻譯。本節有五個前面沒討論到、但不先解決就會出事的問題（第一～五節）。

---

## 一、⭐ 認證：共用裝置怎麼知道現在是誰在操作

**這是 index.md 留下的待決問題，而且比想像中關鍵。**

櫃台電腦與走道壁掛平板是**共用裝置**。如果每次操作都要登入，兩週內一定沒人用；如果永遠登入同一個帳號，任務完成者的紀錄就是假的——而那筆紀錄是位階、獎金、感謝卡的來源。

### 解法：分成兩種安全等級

| 場景 | 認證方式 | 為什麼 |
|---|---|---|
| **共用裝置的日常操作**（完成任務、寫備註） | **點頭像切換人，不用密碼** | 螢幕上就兩個頭像，點一下就是你 |
| **員工手機** | 一次登入，PWA 永久保持 | 私人裝置，不用重登 |
| **老吳的後台、病人回饋收件匣、日誌私密內容** | **真的密碼登入** | 這裡才有敏感內容 |

### 為什麼「不用密碼」是安全的

這套系統裡**沒有任何值得偽造的東西**：沒有錢、沒有病人個資、沒有法定出勤紀錄。而且只有 1–2 個人，冒名替對方完成任務沒有動機也沒有意義。

> **把安全成本花在真正需要的地方**（病人回饋、私密日誌、後台），其餘一律降到零阻力。
> 一個每天要輸密碼三次的系統，不管做得多好都會死。

**⚠️ 但共用裝置要有自動歸位**：30 秒不動切回營運視角時，**同時清掉「目前是誰」**，避免下一個人的操作被記在前一個人頭上。

## 二、⭐ 排班表是整個系統的心臟——但它不該用手排

**依賴排班表的東西**：位階計算的分母、`guard_shifts`、診所狀態（準備中／看診中／午休／打烊）、里程碑的參與者、每日日誌的「誰在班」。

如果老吳每個月要手排一次班表，這套系統第三個月就會因為「班表沒排」而全面停擺。

### 解法：**固定班型範本 ＋ 例外登記**

因為班表其實**非常固定**：

| 星期 | 診次 | 誰 | 守備 |
|---|---|---|---|
| 一 | 午診、晚診 | FT | 櫃台＋調劑室 |
| 二 | 早診、午診 | FT | 櫃台＋調劑室 |
| 三 | 午診、晚診 | PT | 櫃台＋調劑室 |
| 四 | 早診、午診 | FT | 櫃台＋調劑室 |
| 五 | 午診、晚診 | FT | 櫃台＋調劑室 |
| 六 | 早診、午診 | FT ＋ PT | 一人櫃台＋調劑、一人櫃台＋診療 |
| 日 | 公休 | — | — |

→ 系統把範本**自動展開成未來的班表**，老吳只在有異動時登記例外：

```
shift_templates（固定班型，設定一次）
        ↓ 自動展開
    實際班表
        ↑ 覆寫
shift_exceptions（請假、代班、國定假日、臨時公休）
```

> **老吳的維護成本 = 只在有事的時候登記一次。** 沒事的月份完全不用碰。
> 未來擴編（忙時段改雙人、增加 PT）也只是改範本，不用重排。

## 三、⭐ 請假必須從**分子與分母同時**扣掉

位階的算法是「該月在某區的守備次數 ÷ 該月排班給她的該區機會 ≥ 50%」。

**如果請假只扣分子不扣分母，生病請假就會拉低比例，變成「生病受罰」。** 那正好踩到我們在 [[600_Projects/平衡木診所遊戲化系統/企劃書/03_獎金對接與八角框架|03]] 明訂不做的黑帽機制（「連續天數斷掉的懲罰會讓人帶病上班」）。

| 情況 | 分母 | 分子 |
|---|---|---|
| 排班且出勤 | +1 | +1 |
| **排班但請假（含特休、病假、國定假日）** | **不計** | 不計 |
| 未排班 | 不計 | 不計 |
| 臨時代班（PT 支援平日） | +1 | +1 |

> 結果：**請假完全不影響位階進度**，它只是讓那個月的進度慢一點點（因為總機會變少）。這是正確的——資歷該反映「排到的班有沒有好好守」，不是「有沒有生病」。

### 出勤怎麼認定？**不做打卡**

`index.md` 已明訂本系統不當法定出勤憑證。所以不做任何打卡動作。

**認定規則：排班表上有她 ＋ 沒有登記請假 ＝ 有守備。** 就這樣。
需要更嚴一點的話，加一個備援條件：當天有完成過任何一個任務。

## 四、⭐ 「一天」的界線用凌晨 4 點，不是午夜

週一、三、五是午晚診到 **21:30**，收診任務可能拖到 22:00 之後才點完。

如果日界線用午夜，遇到延遲收診（例如 23:50 才點完最後一項）就會被算到隔天，導致：當日任務完成率錯誤、每日日誌內容錯亂、盤點日期跑掉。

**建議：營業日界線設在凌晨 4:00（`Asia/Taipei`）。** 凌晨 4 點以前發生的事，都算前一個營業日。

同理，**「月」的界線**（位階計算用）也跟著營業日走，不是曆日。

> 這件事很小，但沒設定的話會在某個延遲收診的晚上默默出錯，而且很難查。

## 五、⭐ 離線可用：設計上已經天然沒有衝突問題

診所 wifi 不穩時，員工點「完成」不能失敗。

### 方案：本機佇列 ＋ 上線後同步

```
點完成 → 立刻寫入本機（IndexedDB）→ UI 馬上給回饋
                ↓ 有網路時
           自動同步到 Supabase
```

### 為什麼不用擔心衝突

因為前面已經定了 **`task_instances` 只增不刪**（見 index.md）——**沒有更新就沒有衝突。** 這是那個設計決策帶來的紅利。

**唯一要處理的是重複提交**（離線時手滑點兩次）：
→ 用 **client 端產生的 UUID** 當主鍵，重送同一個 id 就是冪等，不會產生兩筆。

## 七、權限（RLS）：只嚴管三處，其餘放寬

2 人的診所，過度設計 RLS 只會拖慢開發。

| 嚴格管控 | 規則 |
|---|---|
| `journal_entries` | 可見度=私密 → 只有 owner；可見度=傳承 → 全員可讀 |
| `patient_feedback` | **僅老吳** |
| 後台設定表（`rank_config`、`shop_items`、`dialogue_lines`、`task_templates` 寫入） | **僅老吳** |

其餘表：登入員工可讀寫（本來就是共同工作的紀錄）。

**⚠️ 系統層面不建立「員工效率比較」的任何查詢或畫面**（[[600_Projects/平衡木診所遊戲化系統/企劃書/07_AI背景層|07]] 的鐵則）。這不是權限問題，是**根本不做那個功能**。

## 八、⭐ 備份：接回老吳既有的 Obsidian vault

**這套系統最珍貴的資產是位階日誌、平衡木編年史、感謝卡——那些是不可重建的。** 任務紀錄丟了可以重來，一段別人寫給你的話丟了就是丟了。

Supabase 免費層的備份保障有限，不該把唯一一份資料放在那裡。

### 建議：每週自動匯出到 vault

```
每週日凌晨 → 匯出 JSON/Markdown
   → 寫入 600_Projects/平衡木診所遊戲化系統/備份/
   → Obsidian Git 自動推上 GitHub
```

**這個做法特別合適，因為老吳的 vault 本來就在 git 上、本來就會自動推送。** 等於備份系統已經存在，只要把資料送進去。

而且日誌與編年史匯出成 Markdown 之後，**在 Obsidian 裡本身就可讀可搜尋**——即使有一天系統關掉了，那些文字還在。

## 九、AI 層技術實作

| 項目 | 選用 |
|---|---|
| 排程 | **Supabase pg_cron ＋ Edge Functions**（資料就在旁邊，不用跨服務） |
| 模型 | Claude API |
| 頻率 | 每天 3–5 次（收診後 · 每週日 · 每月底 · 事件觸發 · 老吳手動） |
| 成本 | 估月 NT$100 以內 |
| **降級** | AI 失敗時公佈欄顯示「今天的日誌還在寫」，**核心功能完全不受影響** |

### 鐵則（承 07）

- **統計用 SQL 算，AI 只負責寫成人話。** 讓 AI 心算會出錯，叫貨建議算錯就是真的錢
- **AI 產出一律是草稿**，人按確認（唯一例外：每日日誌自動發布，因為只描述事實、不涉及錢）

## 十一、規模與成本

**資料量極小**：2 人 × 約 10 筆／天 × 365 ≈ **每年 7,300 筆**。Supabase 免費層（500MB）用十年都用不完。

> **效能瓶頸不在資料庫，在前端的小世界動畫。** 資料庫這邊完全不用擔心。

| 項目 | 年費用 |
|---|---|
| Supabase 免費層 | NT$0 |
| Vercel Hobby | NT$0 |
| 網域（選配） | NT$400–800 |
| AI API | 約 NT$1,200 |
| 美術素材（AI 生成迭代） | 一次性 |
| **合計** | **約 NT$2,000／年** |
