# 09 資料模型與技術規格

> 前八節的技術翻譯。本節有五個前面沒討論到、但不先解決就會出事的問題（第一～五節）。

---

## 一、⭐ 認證：共用裝置怎麼知道現在是誰在操作

**這是 index.md 留下的待決問題，而且比想像中關鍵。**

櫃台電腦與走道壁掛平板是**共用裝置**。如果每次操作都要登入，兩週內一定沒人用；如果永遠登入同一個帳號，任務完成者的紀錄就是假的——而那筆紀錄是位階、獎金、感謝卡的來源。

### 解法：分成兩種安全等級

| 場景 | 認證方式 | 為什麼 |
|---|---|---|
| **共用裝置的日常操作**（完成任務、寫備註） | **點頭像切換人，不用密碼** | 螢幕上就兩個頭像，點一下就是你 |
| **員工手機** | 一次登入，PWA 永久保持 | 私人裝置，不用重登 |
| **老吳的後台、病人回饋收件匣、日誌私密內容** | **真的密碼登入** | 這裡才有敏感內容 |

### 為什麼「不用密碼」是安全的

這套系統裡**沒有任何值得偽造的東西**：沒有錢、沒有病人個資、沒有法定出勤紀錄。而且只有 1–2 個人，冒名替對方完成任務沒有動機也沒有意義。

> **把安全成本花在真正需要的地方**（病人回饋、私密日誌、後台），其餘一律降到零阻力。
> 一個每天要輸密碼三次的系統，不管做得多好都會死。

**⚠️ 但共用裝置要有自動歸位**：30 秒不動切回營運視角時，**同時清掉「目前是誰」**，避免下一個人的操作被記在前一個人頭上。

## 二、⭐ 排班表是整個系統的心臟——但它不該用手排

**依賴排班表的東西**：位階計算的分母、`guard_shifts`、診所狀態（準備中／看診中／午休／打烊）、里程碑的參與者、每日日誌的「誰在班」。

如果老吳每個月要手排一次班表，這套系統第三個月就會因為「班表沒排」而全面停擺。

### 解法：**固定班型範本 ＋ 例外登記**

因為班表其實**非常固定**：

| 星期 | 診次 | 誰 | 守備 |
|---|---|---|---|
| 一 | 午診、晚診 | FT | 櫃台＋調劑室 |
| 二 | 早診、午診 | FT | 櫃台＋調劑室 |
| 三 | 午診、晚診 | PT | 櫃台＋調劑室 |
| 四 | 早診、午診 | FT | 櫃台＋調劑室 |
| 五 | 午診、晚診 | FT | 櫃台＋調劑室 |
| 六 | 早診、午診 | FT ＋ PT | 一人櫃台＋調劑、一人櫃台＋診療 |
| 日 | 公休 | — | — |

→ 系統把範本**自動展開成未來的班表**，老吳只在有異動時登記例外：

```
shift_templates（固定班型，設定一次）
        ↓ 自動展開
    實際班表
        ↑ 覆寫
shift_exceptions（請假、代班、國定假日、臨時公休）
```

> **老吳的維護成本 = 只在有事的時候登記一次。** 沒事的月份完全不用碰。
> 未來擴編（忙時段改雙人、增加 PT）也只是改範本，不用重排。

## 三、⭐ 請假必須從**分子與分母同時**扣掉

位階的算法是「該月在某區的守備次數 ÷ 該月排班給她的該區機會 ≥ 50%」。

**如果請假只扣分子不扣分母，生病請假就會拉低比例，變成「生病受罰」。** 那正好踩到我們在 [[600_Projects/平衡木診所遊戲化系統/企劃書/03_獎金對接與八角框架|03]] 明訂不做的黑帽機制（「連續天數斷掉的懲罰會讓人帶病上班」）。

| 情況 | 分母 | 分子 |
|---|---|---|
| 排班且出勤 | +1 | +1 |
| **排班但請假（含特休、病假、國定假日）** | **不計** | 不計 |
| 未排班 | 不計 | 不計 |
| 臨時代班（PT 支援平日） | +1 | +1 |

> 結果：**請假完全不影響位階進度**，它只是讓那個月的進度慢一點點（因為總機會變少）。這是正確的——資歷該反映「排到的班有沒有好好守」，不是「有沒有生病」。

### 出勤怎麼認定？**位階不看打卡**

即使系統有了打卡模組（見第三之二節），**位階計算仍然不使用打卡資料**。

**認定規則：排班表上有她 ＋ 沒有登記請假 ＝ 有守備。** 就這樣。

> ⚠️ **這個分離是刻意的。** 如果打卡遲到 5 分鐘就影響位階，位階就變成懲罰工具——那正是我們一直在避免的東西。
> **打卡資料只用於法定出勤與全勤獎金；位階只看「排到的班有沒有守」。**

## 三之二、⭐ 打卡模組（2026-09-08 老吳決定納入）

> 老吳：「我確認可以搭配打卡系統，只要保存做好。」

### 這不是推翻 index.md，是把兩件事分開

`index.md` 原本的警告是：**不要拿「任務完成的時間戳」當出勤憑證**——那個擔憂仍然成立，而且不變。

現在要做的是**另一件事**：一個專門的、獨立的打卡模組。兩者可以並存：

| | 任務時間戳 | **打卡模組** |
|---|---|---|
| 用途 | 任務軌跡、耗時分析 | **法定出勤紀錄** |
| 法律地位 | ❌ 不是憑證 | ✅ 是憑證 |
| 用於位階 | ✅ | ❌ **不用** |
| 用於全勤獎金 | ❌ | ✅ |

### 法規要求（勞基法第 30 條）

| 要求 | 系統怎麼做 |
|---|---|
| 置備出勤紀錄，**逐日記載至分鐘為止** | 上下班各一次打卡，記到分鐘 |
| **保存 5 年** | 見下方「獨立存活」設計 |
| 勞工請求時應提供**影本** | 員工可自行匯出／列印自己的紀錄 |
| 勞檢時能提出 | 可匯出制式 PDF／CSV |

> 電子化紀錄（電腦、刷卡、打卡鐘）法規上都可以，所以本系統當出勤紀錄**沒有法律障礙**。問題不在能不能，在**穩不穩**。

### ⚠️ 核心原則：打卡模組必須能「獨立存活」

**出勤紀錄是法律文件，它的規格是不可竄改、可稽核、保存 5 年、可列印。**
但遊戲化系統會一直改版、加功能、可能有 bug、可能哪天不玩了。

**把法律文件綁在一個會演化的系統裡，等於把法遵風險放進一個不穩定的地方。**
- 系統當機三天沒人打卡 → 勞檢時無法解釋
- 哪天不玩這套了 → 出勤紀錄怎麼辦？

所以打卡模組要滿足五件事：

| # | 設計 | 說明 |
|---|---|---|
| 1 | **獨立資料表** `attendance` | 與 `guard_shifts`、`zone_ranks` 完全分離，不互相依賴 |
| 2 | **不依賴任何遊戲化邏輯** | 打卡不需要選角色、不需要地圖、不需要任務模式。**一個大按鈕就結束** |
| 3 | **只增不刪** | 補登要新增一筆補登紀錄（誰補、何時補、原因、核可人），不覆蓋原始資料 |
| 4 | ⭐ **每月自動匯出 PDF ＋ CSV 到 vault** | **這才是真正的 5 年保存**，不是靠 Supabase |
| 5 | **紙本備援流程** | 系統壞掉時手寫補登的 SOP，寫進到職訓練 |

> 第 4 條最重要。承第八節的備份設計——每月匯出的出勤表進 `600_Projects/平衡木診所遊戲化系統/出勤紀錄/YYYY-MM.pdf`，Obsidian Git 自動推上 GitHub。
> **即使這套系統五年後整個關掉，那些 PDF 還在你的 vault 裡。**

### 打卡的實務設計

| 問題 | 建議 | 理由 |
|---|---|---|
| **打幾次卡？** | **上班、下班各一次** | 週一三五的 30 分鐘休息、週二四六的 1.5 小時午休，依合約約定自動扣除。要求打四次卡太煩，而且一定會忘 |
| **休息時間有異動怎麼辦？** | 當天登記例外（例如「今天沒休息到」） | 少數情況才需要 |
| **地點限制（GPS／wifi）？** | **建議不做** | 2 人診所沒有作弊動機。真要做的話，用診所 wifi SSID 判斷比 GPS 可靠且省電 |
| **忘記打卡？** | **一定會發生**，要有補登流程 | 員工申請 → 老吳核可 → 留補登痕跡 |
| **遲到怎麼呈現？** | 只記錄事實，**不做任何警示或紅字** | 全勤獎金的判定由老吳月結時看，系統不當場評判 |

> 最後一條要特別注意：**打卡畫面出現「你遲到了 3 分鐘 ⚠️」是最快毀掉整套系統氣氛的一句話。** 系統只記錄，不評判。

### 打卡直接餵養全勤獎金

現有獎金制度的「全勤獎金 2,000/月（當月無遲到、無故缺勤）」，**目前沒有客觀依據**。打卡模組正好填上——這也是納入打卡最實際的價值。

### 資料表

| 表 | 主要欄位 |
|---|---|
| `attendance` | staff_id · 日期 · 上班時間 · 下班時間 · 休息扣除分鐘 · 來源(打卡/補登) · **client_uuid**(冪等) |
| `attendance_corrections` | attendance_id · 申請人 · 原因 · 申請時間 · 核可人 · 核可時間 · 原始值 · 修正值 |
| `attendance_exports` | 年月 · 匯出時間 · 檔案路徑 · 筆數 ← 稽核用，證明有定期保存 |

### ⚠️ 上線前建議跟會計師或勞務顧問確認一次

你已經有接洽的會計師。把「用自建系統作為出勤紀錄」這件事問一次，重點確認：紀錄格式是否符合、匯出的 PDF 形式勞檢能否接受、補登流程是否合規。**問一次的成本很低，事後被開罰很麻煩。**

## 四、⭐ 「一天」的界線用凌晨 4 點，不是午夜

週一、三、五是午晚診到 **21:30**，收診任務可能拖到 22:00 之後才點完。

如果日界線用午夜，遇到延遲收診（例如 23:50 才點完最後一項）就會被算到隔天，導致：當日任務完成率錯誤、每日日誌內容錯亂、盤點日期跑掉。

**建議：營業日界線設在凌晨 4:00（`Asia/Taipei`）。** 凌晨 4 點以前發生的事，都算前一個營業日。

同理，**「月」的界線**（位階計算用）也跟著營業日走，不是曆日。

> 這件事很小，但沒設定的話會在某個延遲收診的晚上默默出錯，而且很難查。

## 五、⭐ 離線可用：設計上已經天然沒有衝突問題

診所 wifi 不穩時，員工點「完成」不能失敗。

### 方案：本機佇列 ＋ 上線後同步

```
點完成 → 立刻寫入本機（IndexedDB）→ UI 馬上給回饋
                ↓ 有網路時
           自動同步到 Supabase
```

### 為什麼不用擔心衝突

因為前面已經定了 **`task_instances` 只增不刪**（見 index.md）——**沒有更新就沒有衝突。** 這是那個設計決策帶來的紅利。

**唯一要處理的是重複提交**（離線時手滑點兩次）：
→ 用 **client 端產生的 UUID** 當主鍵，重送同一個 id 就是冪等，不會產生兩筆。

## 六、資料表總覽（依領域分組）

> 通用約定：所有表都有 `id uuid PK`、`created_at timestamptz`。
> 所有表預留 `clinic_id`（現在只有一家，加這欄成本是零，未來展店不用重寫）。

## 十一、規模與成本

**資料量極小**：2 人 × 約 10 筆／天 × 365 ≈ **每年 7,300 筆**。Supabase 免費層（500MB）用十年都用不完。

> **效能瓶頸不在資料庫，在前端的小世界動畫。** 資料庫這邊完全不用擔心。

### 「年 NT$2,000」指的是什麼（澄清）

那個數字只涵蓋**雲端服務的經常性支出**，不是專案總成本。拆開來看：

| 項目 | 年費用 | 說明 |
|---|---|---|
| Supabase | **NT$0** | 免費層 500MB 資料庫 ＋ 1GB 儲存。以每年 7,300 筆的量，用十年都用不完 |
| Vercel Hobby | **NT$0** | 部署與 CDN |
| 網域（選配） | NT$400–800 | 不買也可以，用 Vercel 給的免費網址 |
| **AI API** | **約 NT$300–1,200** | 見下方估算，我抓的是保守（偏高）值 |
| **小計** | **約 NT$700–2,000／年** | ← 這就是「年 2,000」的來源 |

#### AI API 的實際估算

| 用途 | 頻率 | 每次輸入量 |
|---|---|---|
| 每日診所日誌 | 30 次／月 | 約 3K token（當天的任務、備註、班表、投稿） |
| 每週報 | 4 次／月 | 約 10K |
| 每月結（庫存、叫貨建議） | 1 次／月 | 約 20K |
| 台詞候選、里程碑小故事 | 不定 | 小 |

粗估每月約 150K input token ＋ 少量 output。以目前 Claude 的價格算，**一個月不到 US$1，一年約 NT$300–400**。

> 我在表上寫 NT$1,200 是刻意高估留餘裕。而且如果每日日誌改用較便宜的模型，還會更低。**這是這個專案最不需要擔心的一項成本。**

### ⚠️ 但「年 2,000」**不包含**這些

| 項目 | 費用 | 性質 |
|---|---|---|
| **走道壁掛平板 ＋ 掛架** | 約 NT$5,000–15,000 | **一次性**，見 08 的採購提醒 |
| **該位置的電源施工** | 併入裝修 | **一次性，且現在就要決定** |
| **Typeless Pro** | 年繳約 US$12/月 ≈ NT$4,600／年 | **經常性**（你已決定付） |
| 美術素材生成工具 | 你現有的訂閱 | 可能已在付 |
| **開發人力** | **NT$0** | 與 Claude Code 協作，成本是你的時間 |

**所以更完整的說法是：**

| | 金額 |
|---|---|
| **一次性投入**（平板、掛架、電源） | 約 NT$5,000–15,000 |
| **每年經常性支出**（雲端 ＋ Typeless） | 約 NT$5,300–6,600 |
| 開發人力 | 你的時間 |

> 其中 Typeless 佔了經常性支出的七成以上——**而它是可以先用免費層跑的**（8,000 字／週）。
> 真正屬於這套系統本身的年支出，仍然在 NT$2,000 以內。
